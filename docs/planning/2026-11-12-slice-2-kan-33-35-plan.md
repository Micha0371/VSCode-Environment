# Slice 2 follow-ups: one edit screen per tap, and a clean close after remove — plan

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:executing-plans (recommended here) or superpowers:subagent-driven-development. Steps use checkbox (`- [ ]`) syntax.

**Goal:** A tap on a Pantry or Shopping row opens exactly one edit screen, and a successful remove closes either edit screen without showing or announcing the "no longer available" state. Then the same build runs on the physical phone, including a fast double tap.

**Tickets:**
- KAN-33 (PF-NAV-001: Fast double tap on a list item opens its edit screen twice), Medium, functional defect;
- KAN-35 (PF-UI-001: Edit screen briefly shows "no longer available" after a successful remove), Low.

Fixing KAN-33 is what keeps KAN-15 ([Slice 2] Shopping List Mobile UI) open.

**Spec:**

## What exists

  - `app/(tabs)/shopping.tsx:157`: `onPress={() => router.push(`/shopping-item/${item.id}`)}`.

  Neither has a guard. Two taps before the first navigation completes push two modal screens for the same item. The second screen hydrates with the old name, so saving there after a rename in the first screen reverts it.

During the dismissal animation the missing state is visible, and on Shopping a screen reader may announce it.

## Global constraints

- **KAN-33 exclusions:** no navigation-framework change, and no redesign of the list or edit screens.
- **KAN-35 exclusion:** no change to provider delete semantics.
- **Test first:** each fix has failing tests first, for both lists and both edit screens, shown red on the current code.
- **Device scope:**
  - only the test APK (`com.pantryflow.test`);
  - only local Supabase, through the loopback proxy and `adb reverse`;
  - reserved fixture accounts, with exact cleanup.
- **No iOS or macOS CI.**

## Review focus

1. **A dead list after a navigation that never happened.** If `push` doesn't move focus away (for example, the route is rejected), the lock must not stay on forever. A fallback releases it.
2. **Reopening after close.** After the edit screen closes and the list regains focus, a single tap opens it again. This is KAN-33's second criterion.
3. **Two different rows tapped quickly.** Only one edit screen opens. The lock is per list screen, not per item.
4. **A genuinely missing item still shows the missing state.** That covers an item deleted elsewhere, and a remove that fails because the row is already gone. KAN-35's second criterion.
5. **A failed remove for another reason** keeps the form, its values and the translated error, as today.

### Task 1 (KAN-33): one edit screen per tap

**Files:**
- Create: `pantry-flow/hooks/useSingleOpen.ts`;
- Modify: `pantry-flow/app/(tabs)/index.tsx`, `pantry-flow/app/(tabs)/shopping.tsx`;
- Test: `pantry-flow/tests/single-open.test.cjs` (new), `tests/shopping-screen.test.cjs`, `tests/screens.test.cjs`.

**Interface:**
- Produces `useSingleOpen(): (route: string) => void`, with these rules:
  - the first call pushes `route` and locks;
  - further calls are ignored while locked;
  - the lock is released when the screen regains focus after a blur, through the `useFocusEffect` setup;
  - if the screen never blurred within 1000 ms of the push, a fallback releases the lock;
  - the timer is cleared on unmount.
- Consumes `useRouter().push` and `useFocusEffect` from `expo-router`.

    - unmount clears the timer.

## Rulings and risks carried into execution

- **Execution mode:** inline, as in step 5. Two small code tasks and a device task that needs the phone in the loop. A Sonnet task review covers Tasks 1–2, and an Opus final review covers the branch.
- **The lock is released on focus, with a 1000 ms fallback.** A timer alone would reopen the race on a slow transition, and focus alone could leave the list dead if no navigation happened.
  - Cost if wrong: a second tap ignored for up to a second after a navigation that silently failed.
- **`removing` renders an empty background, not the frozen form.** That needs no snapshot of the deleted item, and nothing interactive remains during the close.
  - Cost if wrong: an empty frame during the dismissal animation, which is visually the same as the background.
- **The flash isn't asserted on a device.** It lasts one animation, and a Maestro check on it would be flaky. The screen tests are the evidence.
- **Phone needed for Task 3 (about 1 hour, including the build):** charger, Stay awake, Wi-Fi ADB with a fresh port, and `adb reverse` set again. The Maestro driver is already installed.
